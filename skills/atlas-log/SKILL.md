# Atlas Log

You maintain the project journal at `docs/atlas/journal/`. The journal records the trajectory of work as it happens. One file equals one work unit: from plan (via grill-me) through execution to closure.

## Naming: slug is the menu signal

The slug becomes the filename, the auto-derived (or explicit `--title`) title shows up in `atlas-orient`'s active and recent listings, and the agent decides whether to read the entry based on that signal.

**Rules:**

- **Slug states the work, not the topic.** Journals describe *work units*, so slugs should be action-bearing: `add-X`, `refactor-Y`, `investigate-Z`, `migrate-A-to-B`, `strip-X-from-Y`. Topic-label slugs (`logging`, `auth-stuff`, `frontend-things`) fail.
- **Self-contained.** Readable without other context. `fix-bug-123` is bad (what bug?); `fix-cuda-graphs-dispatch-race` is good.
- **Specific enough to disambiguate from sibling work.** If you have three journal entries this week about `atlas`, none should just be `atlas`.
- **kebab-case-words ≤ ~50 chars.** Longer is a signal the slug is trying to be a sentence — tighten.

**Examples:**

| Good | Bad | Why bad |
|---|---|---|
| `strip-framework-vocab-from-substantive-chat` | `transparency-fix` | doesn't say what was stripped or where |
| `enforce-orient-and-interview-skills` | `skill-updates` | which skills? what enforced? |
| `script-driven-journal-writes` | `journal-stuff` | doesn't name the work |
| `cuda-graphs-dispatch-p99-regression` | `perf-bug` | which subsystem? which metric? |

## Section convention: first sentence of Context carries the work

The first sentence of `## Context` is what `atlas-orient` pulls into its active/recent listings. Make it independently readable — a stranger reading just that sentence should know what this work unit is. The rest of Context can elaborate.

## Mental model

Each journal entry has a simple lifecycle:

- **Created** by grill-me (with the Plan section), OR by you directly via `open.py` if work starts ad-hoc
- **Updated** by you as work progresses, by calling `append.py` to add timestamped subsections under `## Work log`
- **Closed** by you via `close.py` when the work unit ends, with the Close section and `verification-result` set

Multiple entries can be `active` at the same time — parallel work across windows / topics is normal. You hold "which entry am I currently working on" in your own conversation state. Do not assume there is only one.

## All journal mutations go through scripts

All frontmatter timestamps (`opened`, `closed`, and the `### YYYY-MM-DD HH:MM` work-log headers) are generated by `datetime.now()` inside the scripts. The agent **never** writes timestamps by hand. This is the load-bearing rule of this skill — the scripts exist specifically because agent-fabricated timestamps caused real bugs.

**Script-owned fields — never touch with Edit / Write**: `opened`, `closed`, `status`, `verification-result`, and the `### YYYY-MM-DD HH:MM` Work log headers. They change only through `open.py` / `append.py` / `close.py`. Everything else is yours to edit normally: body prose (Context, Plan sections, typo fixes) and the `tags` / `related` frontmatter fields.

Auto-reindex is built into all three scripts — you do not need to call `reindex.py` separately after a mutation.

## Trigger: when to APPEND (do automatically, no pre-confirmation)

Append a Work log subsection whenever any of these happen:

- You completed a substantial unit of work (function written, bug fixed, refactor committed, benchmark run with a result)
- A non-trivial decision was made mid-work (then also consider invoking `atlas-entity` for a D-NNN if it qualifies)
- A new unresolved question surfaced (then also consider a Q-NNN)
- An experiment produced a result (then also consider an E-NNN)
- The user explicitly says "log this" / "记一下" / "write that down"

After appending, **say nothing about the append**. It is bookkeeping; the record reaches the user through the work unit's commit, not through chat. If what you logged is worth telling the user right now — a benchmark result, a conclusion — it belongs in your normal reply *as work content*, unwrapped, never as a "(logged: …)" line. Pre-hoc confirmation is equally forbidden — it kills the flow. The framework speaks only when it needs the user; see `using-atlas`'s "Speak in plain project language" for the full list of speak-moments.

## Trigger: when NOT to append

- Trivial conversational exchanges (yes/no, clarifying questions)
- Reading files without producing output
- Looking up information without acting on it
- The user is in rapid-fire question mode
- Tool calls that don't represent work progress (e.g. `ls`, `grep` for orientation)

When unsure, **lean toward NOT logging**. Over-logging is noise; the journal should read like a coherent narrative, not a tool-call log.

## How to APPEND

Pipe the body via stdin to `append.py`:

```bash
echo "$body" | python3 ~/.claude/skills/atlas-log/scripts/append.py \
    --slug <bare-slug>
```

- `--slug` takes the bare slug, no date prefix (e.g. `cuda-graphs-dispatch`, not `2026-05-27-cuda-graphs-dispatch`)
- Body via stdin avoids shell quoting issues with multi-line markdown / Chinese / quotes
- Timestamp is `datetime.now()` automatically; pass `--at "YYYY-MM-DD HH:MM"` only when backfilling
- Reindex is automatic

For multi-line bodies, prefer heredoc over `echo`:

```bash
python3 ~/.claude/skills/atlas-log/scripts/append.py --slug cuda-graphs-dispatch <<'EOF'
P99 latency 30.9ms → 27.4ms after enabling graph capture for the hot path.
Target was 28ms; we hit it with margin.
EOF
```

The script prints the timestamp it wrote (e.g. `2026-05-27 16:20`). Errors go to stderr with `ERROR:` prefix and non-zero exit.

## Trigger: when to CLOSE

Close an active entry when:

- The Verification criteria (from Plan section) have been checked and the result is known
- The user explicitly says "wrap this up" / "结束了" / "close this entry" / "关了吧"
- Topic clearly switched and the previous entry will not be resumed (confirm with user first)
- The entry has been stale for >3 days and the user confirms it's done

**Closing entries with no formal Verification (opened via `open.py`, not `grill-me`):** these entries have only Context + Work log, no Plan / Verification section. The default close criterion is **implementation done + no obvious gaps + relevant validators pass** — e.g. edited skill files: skills still validate and grep confirms changes landed; created entity: `validate.py` and `reindex.py` clean; wrote a script change: script runs without error and output looks right. Make the judgment, close, announce — symmetric with append (no pre-confirmation). Do not wait for the user to bless every close; if you genuinely don't know whether the work is done, surface that explicitly instead of leaving the entry hanging.

Be consistent across the session: don't close one entry on your own judgment, then sit on the next one waiting for approval, unless the second entry genuinely has a verification gap. Inconsistency is its own failure mode.

Closing is **sticky** — once closed, the entry is frozen and append-only via the script (which refuses to write to closed entries). If related work resurfaces later, open a new entry and link via `related` frontmatter.

### When a continuation is NOT a new work unit

The "closed-is-sticky, open a new entry with `related:`" rule is for work that resurfaces **later** — different session, days/weeks gap, new sub-thread. It is NOT for these cases:

- **Same-session refinement** — user gives feedback minutes after close that requires editing files you just touched. This is v2 of the same work unit; the closed entry stays accurate as v1, the commit history captures the recalibration. Just do the edits.
- **Direct continuation of a just-closed unit** — you finish A, close it, the user immediately says "now also do A.adj where adj is a small tweak". Same unit. Edit; do not re-open.
- **Reverting / undoing your own in-session work** — you wrote X, the user said no, you delete it. No entry needed.

If you find yourself about to open a new entry within minutes of closing the previous one on the same conversation thread, stop. Ask: is this really a new work unit, or am I being reflexive? Default to "just edit." `git log` is the trail. The journal records work units, not every conversational micro-iteration.

### Confirmation rules

**If the user has explicitly commanded close**, that IS the confirmation. Do not show a draft of the Close section in chat for the user to approve — just write it and run `close.py`, silently. The wrap-up you would naturally give as a teammate (what was done, whether verification passed) is the user-facing summary; the close record itself rides the commit. Drafting-and-showing on top of an explicit command is noise.

**If you are proposing close** (e.g. detected stale entry, or you believe verification is complete and want to surface that), THEN confirm before writing. Phrase the proposal in plain terms ("I think the bug-fix work is done — want me to wrap it up?"), not framework terms ("entry X is ready to close"). The Close section content can be discussed in chat first.

## How to CLOSE

Pipe the Close section body via stdin to `close.py`:

```bash
python3 ~/.claude/skills/atlas-log/scripts/close.py \
    --slug <bare-slug> \
    --result {passed|failed|partial} <<'EOF'
**Outcome**: <one sentence on whether the work succeeded>

**Verification result**: <reference to Plan's Verification criteria>

**Keepers (finalized)**:
- <what actually got into long-term regression>

**Throwaways (deleted)**:
- <what was removed>

**Spawned entities**:
- <new D / E / Q created during this work; closed Q's>
EOF
```

The script sets `status: closed`, `closed: <now>`, `verification-result: <result>` in the frontmatter, appends the Close section to the body, and reindexes. Prints the close timestamp on stdout.

`--result` choices: `passed` | `failed` | `partial`. Refuses to close an entry that is already closed.

## Identifying the active entry

Before appending or closing, you must know which slug to pass. Sources in priority order:

1. **Your conversation memory** — if `open.py` or grill-me was called earlier in this conversation, the slug is the entry it created. Hold it through the session.
2. **User reference** — user says "log to the cuda-graphs entry" or "close the bench entry"
3. **Active entries list** — run:
   ```bash
   grep -l "^status: active" docs/atlas/journal/*.md
   ```
   If exactly one matches, that's it. If multiple, ask the user once and carry the answer.

### Fallback: bootstrap an entry if none exists

The canonical bootstrap path is `using-atlas` at session start. If it was skipped or deferred and you reach a moment where an append is warranted, bootstrap via `open.py`:

```bash
python3 ~/.claude/skills/atlas-log/scripts/open.py \
    --slug <kebab-case-slug> \
    --tags <comma,separated,tags> <<'EOF'
<one paragraph describing what this work is about>
EOF
```

The project name is derived from PROJECT.md's H1 automatically; pass `--project` only to override. Optional: `--related slug1,D-007` and `--title "Override default title"`.

Then append normally — no announce; the entry travels with the work's commits.

If you find yourself using this fallback frequently, using-atlas probably isn't getting invoked at session start — surface that to the user.

## Anti-patterns

- **DO NOT** ask "would you like me to log this?" before every append. Just do it.
- **DO NOT** announce appends, opens, or closes ("(logged: …)", "(opened …)", "(closed — passed)"). Operations are silent; results that matter go in your normal reply as work content. Speak about the journal only when you need the user (close proposals, binding ambiguity).
- **DO NOT** append a journal entry for every tool call. Tool calls are not work units.
- **DO NOT** show the Close section as a chat draft when the user has explicitly commanded close. Just write it.
- **DO NOT** use Edit / Write on script-owned fields (`opened` / `closed` / `status` / `verification-result` / Work log timestamp headers). Body prose and `tags` / `related` are editable normally; timestamps come from `datetime.now()` inside the scripts.
- **DO NOT** hand-write timestamps into argv either (e.g. `--at "2026-05-27 14:00"` as the default). `--at` is for explicit backfill only; the default — `datetime.now()` inside the script — is what you want in the normal case.
- **DO NOT** create a new entry when work is continuation of an already-active one — append to the existing one.
- **DO NOT** edit a closed entry's body. If new info comes up, open a new entry and use `related: [<old-slug>]` to link back.
- **DO NOT** assume only one active entry exists. Always check.

## Cross-references

- `grill-me` creates an entry with Plan section (via `open.py`); this skill takes over from there
- `atlas-entity` is invoked when journal content warrants spawning a D / E / Q
- `atlas-orient` reads journal frontmatter directly to load session context (`_index.md` is a human-only browse view)

## What this skill does NOT do

- Does not produce Plans — that's `grill-me`'s job
- Does not manage D / E / Q entities — that's `atlas-entity`
- Does not propose long-form topic distillation — that's `atlas-compact`
