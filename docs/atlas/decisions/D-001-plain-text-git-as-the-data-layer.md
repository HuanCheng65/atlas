# Plain text + git as the data layer

## Context

Atlas needs cross-session state: decisions, experiments, open questions, and
journal entries. Candidate backends included SQLite, a vector DB (for semantic
retrieval), and plain markdown with YAML frontmatter versioned in git.

## Decision

Store all atlas state as plain-text markdown with YAML frontmatter, versioned
in the project's own git repository. No SQLite, no vector DB.

## Rationale

- Plain text survives tool churn; readable forever, zero migration risk.
- `git diff` makes every state change auditable; `git log` is the history.
- ripgrep + frontmatter handles ~80% of retrieval at zero infrastructure cost.
- One repo = one source of truth; nothing extra to back up or sync.
- Trade-off accepted: no native semantic search (mitigated by ripgrep, and an `atlas-search` skill later if needed).

## Consequences

- Schema enforcement lives in `validate.py`, not a DB.
- Indexes (`_index.md`) are derived views regenerated by `reindex.py`.
- Hard constraint propagates: runtime dependencies stay limited to Python + pyyaml + bash.

## Alternatives considered

- SQLite for entities — rejected; loses plain-text + git diff + tool portability.
- Vector DB for journal retrieval — rejected; maintenance overhead and opacity outweigh the marginal recall gain.

Evidence: `docs/design.md` "Trade-offs and rejected alternatives" (SQLite, Vector DB bullets); `PROJECT.md` Hard constraints.
